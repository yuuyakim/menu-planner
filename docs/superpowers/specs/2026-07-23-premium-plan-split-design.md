# プレミアムプランの機能差分（free / premium の線引き）設計

- 日付: 2026-07-23
- 対象: `menu-planner`（献立くん）
- 状態: 設計確定・未実装
- 前提: `docs/superpowers/specs/2026-07-23-premium-entitlement-design.md`（エンタイトルメント基盤）
  および `docs/legal/`（法務ドキュメント）

## 1. 背景と目的

エンタイトルメント基盤の設計14章「未決事項」に残っていた3件のうち、価格（月額300円）と
販売主体（個人事業主本人）は確定し、`docs/legal/README.md` に記録した。
残る1件が **premium の2つ目以降の機能**、すなわち free と premium の線引きである。

線引きが決まらないと、利用規約4条9項もプランを説明するページも書けず、決済フェーズに入れない。
本設計はその線引きを決める。**決済そのもの（Stripe 接続・Webhook・カスタマーポータル）は扱わない。**

## 2. スコープ

### 対象

- free と premium で何が違うかの確定
- 買い物リストの永続化（premium）。チェック状態の保存と、品目の追加・削除
- 週間献立の保存上限を premium で 50 件にする
- 課金導線をどこに出すか
- `spec.md` への反映（2.7 / 2.8 の更新、プレミアムプランの章）

### 対象外

- 決済事業者の接続、Webhook 受信、カスタマーポータル、申込み画面
- 献立マスタに関わる改善（利用者レビューの A / C / D / E）。**すべて free に入れる**（3.2）
- 買い物リストの分量表示（`spec.md` 14.2 で持たないと決定済み）
- 価格の実額計算（利用者レビューの H。C に吸収して決着済み）

## 3. 設計判断

### 3.1 premium は2機能に絞る（決定）

premium は次の2つだけとする。

1. 週間献立の保存上限を 10 件から 50 件にする
2. 買い物リストを永続化する（チェック状態の保存、品目の追加・削除）

**両方とも「毎週の買い物」という定期的な行為に紐づく点が要点である。**
週の献立を組み、リストを持って店に行くというループが月に4回まわる。
一度使うとリストが手元にある状態が当たり前になるため、解約の動機が生まれにくい。
単発の便利機能をいくら並べても、月額課金の理由にはならない。

数を増やさないのは、premium が何であるかをぼかさないためである。

### 3.2 利用者が「困る」と言ったことの解消は free に置く（決定）

`task.md`「利用者レビューからの後続タスク（2026-07-22）」の項目のうち、
**C（日常性。フカヒレの姿煮が出る）と D（季節。7月におせち料理が出る）は
新機能ではなく現状の不満の解消である。**

これらを premium 限定にすると「金を払わないと変な献立が出続ける」という構図になり、
無料利用者の体験は相対的に悪化する。基盤設計3.1「プレミアムは上乗せであり取り上げではない」は
既存の上限値を据え置くことだけを指していたが、**今後の改善についても同じ原則を適用する。**

したがって A（モード選択）・C（日常性）・D（季節）・E（画像）はすべて free に入れる。
premium は、無くても困らないが、あると毎週楽になるものだけで構成する。

### 3.3 履歴の上限は据え置く（決定）

上限を引き上げられる余地は、週間献立の保存（10件）と履歴（FIFO 15件）の2つしかない。
お気に入りは元々上限が無い（`spec.md` 2.6）。

**このうち履歴は据え置く。** 履歴は利用者が意図せず自動で溜まるもので、
`spec.md` 2.5 が FIFO を選んだのも「押し出されても困らない」という判断による。
困らないものを増やしても価値にならず、premium の説明を薄めるだけである。

### 3.4 買い物リストは差分だけを保存する（決定）

`spec.md` 2.8 は「買い物リストは保存しない。開いたときに毎回作り直す。
二重に持つと更新漏れの余地だけが増える」と決めている。**この判断は維持する。**

永続化するのは**献立由来のリストからのズレだけ**とする。
リスト本体は従来どおり週間献立から毎回導出し、そこに差分を重ねて表示する。

- チェックを付けて初めて、その品目の差分行ができる
- 自分で足した品目は `manual` の差分行として持つ
- 「家にあるから消す」は `hidden` の差分行として持つ

こうすれば献立マスタの食材が変わってもリスト本体は追随し、二重管理も生じない。
スナップショットとして全品目を保存する案は、2.8 が避けた二重管理をそのまま導入することになるため採らない。

### 3.5 API は一括置換にする（決定）

差分の更新は、品目ごとの部分更新ではなく**オーバーレイ全体の一括置換**とする。

買い物リストは1人が1端末で使うものであり、品目数も20件程度である。
部分更新にすると競合制御の設計が要るが、それに見合う同時編集の実態がない。
一括置換なら冪等で実装も単純になる。

複数の端末で同時に開いた場合は後勝ちになる。**これを許容する。**
問題が実際に起きたら品目単位の更新に変える。

### 3.6 課金導線は文脈に触れたときだけ出す（決定）

導線は2箇所に限る。

- 週間献立の保存が上限に達したとき（409 を返す場面）
- free の利用者が買い物リストのチェックを付けたとき。**1回だけ**表示し、閉じたら記憶して再表示しない

常設のバナーやメニュー項目は置かない。
利用者レビューで「マスコット（こんたてん）のかわいさ」は明示的に褒められた性質であり、
`task.md`「維持すべき性質」に挙がっている。全画面に常時セールスを重ねるとこれを削る。

### 3.7 premium 専用の画面は作らない（決定）

買い物リストは free と同じ画面を使い、チェックが残るかどうかだけが違う。
専用画面にすると free の利用者から見て「行けない場所」ができ、疎外感が出る。
基盤設計10章がバッジだけに留めたのと同じ理由である。

## 4. free と premium の線引き

| 機能 | free | premium |
| --- | --- | --- |
| 献立検索（1食分 / 1週間分） | ○ | ○ |
| レシピサイト3件の提示 | ○ | ○ |
| 履歴 | 15件（FIFO） | 15件（FIFO） |
| お気に入り | 上限なし | 上限なし |
| 必要食材の表示 | ○ | ○ |
| 買い物リストの生成 | ○ | ○ |
| **買い物リストのチェック状態の保存**（保存済みの週） | × | **○** |
| **買い物リストへの品目の追加・削除**（保存済みの週） | × | **○** |
| 手持ちの食材から探す | ○ | ○ |
| 役割（主菜/副菜/汁物）による絞り込み | ○ | ○ |
| **週間献立の保存** | **10件** | **50件** |
| 今後の改善（モード選択・日常性・季節・画像） | ○ | ○ |

未認証で使える範囲は現状のまま変えない。買い物リストの生成は未認証でも使えるが、
永続化はユーザーに紐づくため認証が要る。

**永続化の対象は保存済みの週間献立に限る。** 差分は週間献立に紐づけて持つため（5.1）、
保存していない週にはぶら下げる先がない。組んだ週をまず保存し、そこから買い物リストを開く、
という流れになる。これは制約であると同時に、premium の2機能が
「週を保存する → リストを持って店に行く」という1つの流れに乗ることを意味する。

## 5. データモデル

### 5.1 マイグレーション `000011_create_shopping_list_overrides`

| カラム | 型 | 制約 |
| --- | --- | --- |
| `saved_weekly_menu_id` | uuid | PK, `REFERENCES saved_weekly_menus(id) ON DELETE CASCADE` |
| `name` | text | PK |
| `category` | text | NOT NULL |
| `origin` | text | NOT NULL（`derived` / `manual`） |
| `checked` | boolean | NOT NULL DEFAULT false |
| `hidden` | boolean | NOT NULL DEFAULT false |
| `created_at` | timestamptz | NOT NULL DEFAULT now() |
| `updated_at` | timestamptz | NOT NULL DEFAULT now() |

- **主キーは `(saved_weekly_menu_id, name)` の複合**とする。同じリストに同名の品目は作れない。
  献立由来の品目と同名の手動品目が並ぶことを DB が防ぐ。
- 週間献立が消えれば差分も消える（`ON DELETE CASCADE`）。差分だけが残っても意味を持たない。
- `origin` は CHECK 制約ではなくアプリ側で検証する。既存テーブル（`menus.role` ほか）の流儀に合わせる。
- **行が無いことが「献立由来のまま・未チェック」を意味する。** 差分表であり、リストの実体ではない。

### 5.2 マイグレーション番号（重要）

基盤設計4.2 と同じ事故の余地がある。golang-migrate は適用済みバージョンを1つの数値で持ち、
現在値より大きいものだけを適用するため、**番号の大きいものが先に本番へ入ると、
後から来る小さい番号は永久に適用されない。**

現時点の採番は次のとおり。

| 番号 | 内容 | 所在 |
| --- | --- | --- |
| `000009` | `add_menu_role` | `feature/menu-role`（未マージ） |
| `000010` | `create_subscriptions` | `feature/premium`（未 push） |
| `000011` | 本設計 | 本ブランチ |

`feature/premium` を `main` にマージする前に、**`000009` と `000010` が
その順序で `main` に入っていることを確認する。**

## 6. ドメイン層

### 6.1 `domain.Entitlement` の拡張

```go
func (e Entitlement) SavedWeeklyMenuLimit() int          // free:10  premium:50
func (e Entitlement) CanPersistShoppingList() bool       // free:false  premium:true
```

基盤設計5.2 と同じく、**フィールドではなくメソッドで導出する。**
`Entitlement{}` のゼロ値では `plan` が空文字となり free と同じ扱いに落ちるため、
取得し忘れても権限が漏れない。`CanPersistShoppingList()` は false 側が安全なので、
この性質がそのまま働く。

### 6.2 `domain.ShoppingListOverride`

`saved_weekly_menu_id` / `name` / `category` / `origin` / `checked` / `hidden` を持つ値オブジェクト。
`origin` は `OriginDerived` / `OriginManual` の2値。

## 7. サービス層

### 7.1 `service.ShoppingListOverrideStore`（ポート）

```go
type ShoppingListOverrideStore interface {
    FindBySavedWeeklyMenu(ctx context.Context, id domain.SavedWeeklyMenuID) ([]domain.ShoppingListOverride, error)
    Replace(ctx context.Context, id domain.SavedWeeklyMenuID, overrides []domain.ShoppingListOverride) error
}
```

`Replace` は当該週間献立の差分を丸ごと置き換える（3.5）。1トランザクションで削除と挿入を行う。
エラーはインターフェースの持ち主である service 側で定義する（`ports.go` 冒頭の方針）。

### 7.2 `ShoppingListService` の変更

買い物リストの導出は既存のまま。取得時に差分を重ねる。

```go
func (s *ShoppingListService) For(ctx, userID, savedWeeklyMenuID) (ShoppingList, error)
func (s *ShoppingListService) ReplaceOverrides(ctx, userID, savedWeeklyMenuID, overrides) error
```

- `For` は `Entitlements.For` を引き、premium のときだけ差分を重ねる。
  free では従来と完全に同じ結果になる。
- `ReplaceOverrides` は premium でなければ `ErrPremiumRequired` を返す。
- **手動品目は1リストあたり100件を上限**とし、超過は `ErrShoppingListItemLimitReached` を返す。
  無制限の利用者由来レコードは Neon の無料枠に対して無防備であり、
  上限そのものに意味はないが、歯止めとして置く。
- 所有者の検証は既存の週間献立の取得と同じ経路を通す。他人のリストは触れない。

## 8. API

### 8.1 既存エンドポイントは変えない

`POST /api/v1/shopping-list` は複数の献立IDから買い物リストを導出するステートレスな API で、
未認証でも使える。**この形も挙動も変えない。** 未保存の週間献立からリストを作る経路はここを通り続ける。

### 8.2 追加するもの

`api/openapi.yaml` に次を追加する。

| Method | Path | 認証 | 説明 |
| --- | --- | --- | --- |
| GET | `/saved-weekly-menus/{id}/shopping-list` | 要 | 保存済みの週の買い物リスト。導出結果に差分を重ねて返す |
| PUT | `/saved-weekly-menus/{id}/shopping-list` | 要 | 差分を一括で置き換える。free は 403 |

- 導出そのものは既存のサービスを再利用する。差分の重ね合わせを**サーバ側で行い、
  フロントには最終形だけを渡す。** マージ処理を TypeScript に持つと、
  既存の `POST /shopping-list` の経路と二重に実装することになる。
- `GET` は free でも呼べる。差分が重ならないだけで、応答の形は同じ。
  フロントに分岐を持たせないため、**プランによって形を変えない。**
- `PUT` の 403 は「プレミアムプランが必要」を意味する。既存の RFC 7807 の形に載せる。
- 手動品目の上限超過は 409（既存の保存上限と同じ扱い）。
- `make gen-api` で TypeScript の型を再生成し、契約テストで仕様と実装のズレを検出する。

## 9. フロントエンド

- 買い物リスト画面は free / premium で同じ。premium のときだけ、
  チェックの変更が `PUT` に反映され、品目の追加・削除の UI が出る。
- free で初めてチェックを付けたとき、案内を1回だけ表示する。
  表示済みであることは `localStorage` に持つ。**サーバに持たせる必要はない**
  （端末ごとに1回で足り、消えても実害が「もう一度出る」だけのため）。閉じたら再表示しない。
- 週間献立の保存が上限に達したときのメッセージは、サーバがプラン由来の件数を返す既存の仕組みに乗せ、
  そこに案内を添える。フロントは件数を持たない。
- プレミアムのバッジ表示は基盤設計10章のまま変えない。

## 10. テスト戦略

既存の TDD 方針（`spec.md` 9章）に沿い、🔴テスト → 🟢実装の対で進める。

| 層 | 検証すること |
| --- | --- |
| domain | `CanPersistShoppingList()` の導出。**ゼロ値の `Entitlement` が false を返すこと** |
| repository | スキーマ検査（既存 `*_schema_test.go` の流儀）、`Replace` が差分を丸ごと置き換えること、CASCADE |
| service | free が `ErrPremiumRequired`、手動品目100件の境界、他人のリストに触れないこと、free の `For` が従来と同一の結果を返すこと |
| handler | 403 と 409 の写像、契約テスト |
| frontend | free ではチェックが保存されないこと、premium では保存されること、案内が1回だけ出ること |
| E2E | premium ユーザーでチェックを付け、**リロード後も残っていること** |

E2E の観点は「リロード後も残る」に絞る。この機能の本体がまさにそこであり、
それ以外（品目の追加など）は service とフロントの単体で足りる。
premium ユーザーは `docker compose exec backend go run ./cmd/grant` で作る（基盤設計11章と同じ）。

## 11. 実装順序の見取り図

詳細な計画は writing-plans で作成する。おおよその依存順序は次のとおり。

1. `domain.Entitlement.CanPersistShoppingList()` と `SavedWeeklyMenuLimit()` の premium 値
2. `domain.ShoppingListOverride`
3. マイグレーション `000011` とスキーマ検査テスト
4. `repository.ShoppingListOverrideRepository`

6. `openapi.yaml` の更新、handler、型の再生成
7. フロントエンド（チェックの永続化 → 品目の追加・削除 → 案内）
8. E2E
9. `spec.md` の更新（2.7 / 2.8 とプレミアムプランの章）
