# 食材テキスト解決のレート制限（ブレスト途中・設計未確定）

- 日付: 2026-08-03
- 状態: **ブレスト途中。案Aの承認待ちで中断。**
- 対象: `POST /api/v1/ingredients/resolve`（`feature/ingredient-text-resolve` で実装済み）
- 目的: LLM 呼び出しのコストが青天井にならないようにする

## なぜ必要か

`/ingredients/resolve` は認証不要で、レート制限は既存の `searchLimit`
（60回/分/IP、`SEARCH_RATE_LIMIT_PER_MIN`）を共有している。これはレシピ検索向けの値で、
LLM を叩くエンドポイントには緩すぎる。

### コスト試算（2026-08-03 実測ベース）

プロンプトを実測した結果:

| 内訳 | 大きさ |
| --- | --- |
| 定型部分（指示文・出力形式） | 256文字 |
| 食材リスト166件 | 644文字（平均3.9文字） |
| 合計（3語のとき） | 1,078文字 / 2,774バイト |

語数を1→20に増やしても約1,130文字にしかならない。**送信量の6割は食材リストで固定。**

Claude Haiku 4.5（入力 $1.00 / 出力 $5.00 per 1M tokens）、1ドル150円として:

| 1回の問い合わせ | 概算 |
| --- | --- |
| 3語（典型） | 約 0.3円 |
| 20語（上限いっぱい） | 約 0.7円 |

> トークン数は文字数からの概算（±30%程度）。**キーを入手したら `count_tokens` で確定させること。**

「読み取る」1回につき LLM 呼び出しは最大1回（未解決語をまとめて送る設計）。
失敗時のリトライが1回だけあるので最悪2回。

**平常時はほとんど LLM に行かない。** ①完全一致で解ける語は問い合わせ自体が発生せず、
②解決キャッシュは利用者ごとではなく**グローバル**（`ingredient_resolutions` は入力語だけがキー）。
誰かが一度解決した語は以後全利用者がキャッシュから引く。「マスタに無い」も保存するので
未知の語も2回目以降は無料。定常状態では試算の1〜3割に落ち着く見込み。

### 悪用されたときの額

問題は平常運転ではなく無認証 × 60回/分:

- 60回/分 × 0.3〜0.7円 = 18〜42円/分
- **1IPあたり 1,000〜2,500円/時間、2.6〜6万円/日**

毎回ランダムな語を投げられるとキャッシュが効かず全部 LLM に行く。
200文字/20語の上限内なら正当なリクエストと区別がつかない。

### プロンプトキャッシュは使えない

Claude Haiku 4.5 のキャッシュ最小サイズは 4,096 トークン。このプロンプトは約1,400トークンで届かない。
`cache_control` を付けても静かに無効になるだけ。

## 決まったこと

1. **制限するのは「読み取る」だけ。**
   「この食材で探す」（`/menus/search-by-ingredients`）は DB を引くだけで料金が増えないため対象外。
   チェックボックスで選んで探す経路は非ログインでも無制限のまま残す。
   これにより `spec.md` 2.9 の「未認証でも使える」を崩さずにコストだけ抑えられる。

2. **非ログインは IP単位・1日あたりで数える。**
   ブラウザ保存（localStorage）はシークレットウィンドウで無限にリセットできるため、
   会員登録への導線にはなってもコスト対策にはならない。
   欠点は共有IP（社内・学校・携帯NAT）で他人と枠を共有すること。

3. **サービス全体の1日あたり上限（サーキットブレーカー）を入れる。**
   会員登録は無料でアカウントをいくつでも作れ、IPも変えられるため、
   利用者ごとの制限は行儀の良い使われ方を整えるだけで総額の天井にはならない。
   全体上限だけが請求額の天井を確定させる。
   超えたら既存の `degraded` 経路で返し、チェックボックスで選んでもらう。

## 未決（ここから再開）

### 案A（推奨）の承認待ち

**案A: DBに日次カウンタを持つ。**
新テーブルに「日付 × キー（IP / ユーザーID / 全体）→ 回数」を持ち、UPSERT で加算する。

推す理由は本番構成。Cloud Run は `min-instances=0`（アイドルでゼロに落ちる）・`max-instances=2` なので、
メモリ上のカウンタは**アイドルのたびに消え、2インスタンスある間は実効上限が2倍**になる。
日次上限としては当てにならず、全体上限に至っては原理的に守れない。

- IPは**サーバの秘密鍵でハッシュ化して保存**する。数を数えるには十分で、
  元に戻せない文字列なのでプライバシーポリシーの改定が要らない。
- 既存の `searchLimit`（分単位・メモリ）はバースト制御としてそのまま残し、
  その上に日次の層を重ねる。

**案B: メモリだけ**（既存 `RateLimiter` の拡張）。実装は最軽量だが上記の理由で日次・全体上限を守れない。

**案C: 併用**（分単位はメモリ、日次と全体はDB）。案Aは自然とこの形になる。

### 決めていない具体値

- 非ログインの1日あたり回数（利用者の想定は「2〜3回」）
- ログインユーザーの上限（「ちょっときつめのレート制限」とのことで具体値は未定。
  日次の回数か、分あたりの回数か、両方かも未決）
- 全体の1日あたり上限（何円ぶんに相当させるか）
- 上限に達したときの画面の文言。既存の縮退（「一部だけ読み取れました」）とは
  別の文言にしたい（「今日の読み取り上限に達しました。ログインすると増えます」など）
