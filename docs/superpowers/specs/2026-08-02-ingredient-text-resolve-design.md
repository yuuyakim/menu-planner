# 手持ちの食材をテキストで入力する（LLMによる表記揺れ吸収）設計

- 日付: 2026-08-02
- 対象: `menu-planner`（献立くん）
- 状態: 設計確定・未実装
- 前提:
  - `spec.md` 2.9（手持ちの食材から献立を探す。フェーズ13）・5.6（`POST /menus/search-by-ingredients`）。**本設計はその入力手段を1つ増やすものであり、検索そのものには手を入れない**。
  - `spec.md` 3.3（インフラ抽象化）。LLM は `RecipeSearchGateway` と同じくインターフェース越しに扱う。
  - **本アプリで LLM API を呼ぶのはこれが最初**。API キーの管理・コスト・障害時の縮退が新しく必要になる。
- ブランチ: `feature/ingredient-text-resolve`

## 1. 背景と目的

`spec.md` 2.9 は、手持ちの食材の入力を**自由記述にしないと明記している**。

> **入力は自由記述にしない。** 食材は自前マスタ（14.1）なので、「にんじん／人参」「じゃがいも／ジャガイモ」のような表記揺れをこちらで吸収する必要が出る。一致しなかったとき、利用者に理由を説明できない。一覧から選ぶ形なら、選べるものがそのまま探せるものになる。

この判断は当時正しかった。表記揺れの吸収を自前でやるには、別名を人手で列挙して維持し続けるしかなく、それでも漏れたときに利用者へ説明できない。

**LLM はこの制約を解除する。** 「豚こま」「ブタこま」「豚小間」を人手で列挙しなくても、`豚肉` に対応づけられる。本設計は 2.9 の却下理由が技術的に解消されたことを受けて、**チェックボックスを置き換えるのではなく、その前段に自由記述を足す**。

166種を6カテゴリから探してチェックする操作は、冷蔵庫を開けながらやるには重い。「豚こま、玉ねぎ、にんじん、卵」と打てる方が速い。一方で、当時の懸念（一致しなかったときに説明できない）は LLM を入れても消えないため、**解釈結果を利用者に見せて確認させる**形で受け止める。

## 2. スコープ

### 対象

- 新エンドポイント `POST /api/v1/ingredients/resolve`（認証不要）。テキスト → 食材ID の解決。
- 新テーブル `ingredient_resolutions`（解決結果のキャッシュ）。
- `domain.NormalizeIngredientWord`（正規化。①②③で共有する）。
- `IngredientResolveGateway`（LLM の抽象）と実装2種＋スタブ。
- `SearchByIngredientsPage` への自由記述入力欄と、未解決語・縮退の表示。
- eval ハーネス（正解データ50〜100件、`-tags=eval` でのみ実行）。
- `spec.md` 2.9 と `IngredientPicker.tsx` の「自由入力にしない」記述の更新。

### 対象外

- **`POST /menus/search-by-ingredients` の変更**（リクエスト・レスポンスとも現状のまま）。
- **`IngredientPicker.tsx` の変更**（コメント以外）。`selected` を親が持つ構造のため、props を変えずにチェックが入る。
- **`IngredientRepository` へのメソッド追加**。食材マスタは166件で固定的なので、既存の `FindAll` で全件引いて service 側で正規化マップを組む。
- 苦手食材の除外、自然文での献立検索（B2）、献立マスタへの LLM 適用（A1）。いずれも別サブプロジェクト。
- premium との連動。本機能は 2.9 と同じく free / 未認証で使える。

## 3. 設計判断

### 3.1 自由記述は入口であり、結果はチェックボックスに反映する（決定）

自由記述 → LLM が解決 → **既存 `IngredientPicker` のチェック状態が入る** → 利用者が目で確認・修正 → 既存の「この食材で探す」を押す。

チェックボックスを置き換えない。これにより3つが同時に得られる。

1. **確認の場が UI として既に存在する。** 解釈結果を見せる専用画面を作る必要がない。
2. **曖昧な解釈を利用者が直せる。** 「ねぎ」が長ねぎになったとき、玉ねぎに直すのはチェックの付け替えで済む。
3. **LLM が落ちても機能が死なない。** 手動チェックは元から動く。

### 3.2 未一致語は明示し、曖昧語は決め打ちする（決定）

マスタに無い語（マツタケ、パクチー）は `unresolved` として**列挙して見せる**。黙って無視しない（`spec.md` 5.6 が「黙って無視すると、利用者の意図と違う結果を正しい答えとして返すことになる」として同じ立場を取っている）。

一方、解釈が割れる語（「ねぎ」→長ねぎ／玉ねぎ）は LLM が1つに決める。候補を出して選ばせる形は取らない。**3.1 の確認 UI が曖昧さを吸収するため**であり、確認ステップを二重にする必要がない。これにより LLM の責務が「入力語 → 食材ID または null」に閉じ、判定ロジックが1本になる。

### 3.3 解決は ①完全一致 → ②キャッシュ → ③LLM の3段で行う（決定）

```
入力: 「豚こま、玉ねぎ、マツタケ」
  ↓ 分割・正規化（Go、決定的）
  ↓ ① 食材マスタとの完全一致        → 玉ねぎ ✓
  ↓ ② ingredient_resolutions を引く  → （2回目以降）豚こま ✓
  ↓ ③ 未解決だけ LLM へ              → 豚こま→豚肉、マツタケ→null
  ↓    結果を ② に保存
```

**全語が①で解ければ LLM を一度も呼ばない。** 0ms・0円で応答する。②があることで、同じ語は世界で1回しか LLM に問い合わせない。

これは `spec.md` 2.9 が却下した「別名辞書」を、人手ではなく LLM に育てさせる形にあたる。人手の列挙・維持という却下理由がここでも消えている。

### 3.4 分割と正規化のルール（決定）

**分割**は、以下のいずれかを区切りとする。

```
読点「、」 / カンマ「,」「，」 / 改行 / 全角空白 / 半角空白 / 中黒「・」
```

連続した区切りは1つとして扱い、分割後に空になった語は捨てる。**「・」を区切りに入れるのは**、買い物メモの書き方として一般的なため（既存の画面も `使える食材: A・B・C` と中黒で並べている）。区切りを含まない食材名はマスタに存在しないため、誤分割の恐れはない。

**正規化**は分割後の各語に対して行う。

```
1. 前後の空白を除去
2. NFKC 正規化（全角英数→半角、半角カナ→全角カナ）
3. カタカナ → ひらがな
```

3を入れるのは、`ingredients.name_kana` に当たるようにするため。

| 入力 | 正規化後 | 一致先 | 結果 |
| --- | --- | --- | --- |
| 玉ねぎ | 玉ねぎ | `name` | ①で解決 |
| タマネギ | たまねぎ | `name_kana` | ①で解決 |
| たまねぎ | たまねぎ | `name_kana` | ①で解決 |

**①の的中率が上がるほど LLM 呼び出しが減る**ため、投資対効果が高い。小文字化は日本語主体のため入れない。

`domain.NormalizeIngredientWord(s string) string` として置き、**①②③とマスタ側のマップ構築がすべて同じ関数を通る**。別々に実装すると、①で引けなかった語が②でも引けないという穴が開く。

### 3.5 LLM には食材名を渡し、食材名を返させる（決定）

素朴には166件の `{id, name, name_kana}` を渡して `id` を返させる形になるが、UUID は36文字あり、166件で約3000トークンに達する。毎回これを送るのは無駄で、1文字の取り違えが解決失敗になる。

**LLM には食材名のリスト（約1000トークン）だけを渡し、食材名を返させる。** ID への変換は①で作った正規化マップを再利用してアプリ側で行う。

副次的な効果として、**LLM がマスタに存在しない名前を返してもアプリ側で `null` に落ちる**。ハルシネーションが構造的に無害化される。

> Claude Haiku 4.5 のプロンプトキャッシュ最小長は 4096 トークンで、この約1000トークンは**キャッシュされない**。マスタ部分を毎回送るコストはそのまま乗る。

### 3.6 LLM の失敗は部分成功として扱う（決定）

③が失敗しても **200 を返し、①②で解けた分を返す**。レスポンスに `degraded: true` を立て、画面は「一部だけ読み取れました。残りは下から選んでください」と出す。502 で全体を落とさない。

`spec.md` 2.3 が既に同じ立場を取っている。

> 外部APIが失敗した場合は献立の提案自体は成功として扱い、レシピ欄にエラー表示とリトライ導線を出す（レシピ取得の失敗が献立提案を巻き込んで落とさない）

全語が解けなかった場合も `resolved: []`, `degraded: true` の 200 とする。チェックボックスで手動選択できるため、**機能そのものは死なない**。

### 3.7 プロバイダは eval の数字で決める（決定）

候補は **Claude Haiku 4.5**（$1 / $5 per 1M、1回約0.13円）と **DeepSeek V4 Flash**（$0.14 / $0.28 per 1M、1回約0.015円）。約9倍の差があるが、いずれも月数百円の範囲で、**コストだけでは決め手にならない**。

判断を分けるのは以下で、どちらも事前の推測では決まらない。

- **日本語の生活語彙の精度。** 「豚こま」「豚小間」「ブタこま」をどれだけ拾えるか。
- **データの所在。** DeepSeek はプライバシーポリシー上、入力データを中華人民共和国内のサーバーに保存する。本アプリは本番稼働中で未認証公開のため、**採用する場合はプライバシーポリシーの改定が必要**になる。

したがって `IngredientResolveGateway` を挟み、**同一の eval データセットで両方を測ってから本番のデフォルトを決める**。テスト用スタブのためにインターフェースはどのみち必要なので、実装差し替えの追加コストはほぼ無い。

### 3.8 既存の API・コンポーネント・リポジトリに手を入れない（決定）

献立くんは本番稼働中で、`POST /menus/search-by-ingredients` は未認証で公開されている。新機能を独立したエンドポイントに閉じ込めることで、**最悪 `/ingredients/resolve` を無効化するだけで元の状態に戻せる**。

`IngredientService` に相乗りさせないのも同じ理由。あちらは「食材マスタそのもの」と「食材からの献立検索」を担っており、テキスト解決は外部I/Oを2つ（キャッシュ・LLM）新たに抱える。同居させると既存機能のテストに LLM スタブが必要になる。

## 4. バックエンド

### 4.1 `POST /api/v1/ingredients/resolve`（認証不要）

リクエスト:
```json
{ "text": "豚こま、玉ねぎ、マツタケ" }
```

レスポンス（200）:
```json
{
  "resolved": [
    { "word": "豚こま", "ingredient": { "id": "yyy", "name": "豚肉",   "nameKana": "ぶたにく", "category": "meat" } },
    { "word": "玉ねぎ", "ingredient": { "id": "xxx", "name": "玉ねぎ", "nameKana": "たまねぎ", "category": "vegetable" } }
  ],
  "unresolved": ["マツタケ"],
  "degraded": false
}
```

- `word` は**利用者が書いた元の語**を返す（正規化後ではない）。画面で「マツタケ は登録がありません」と出すとき、書いた通りの文字列の方が伝わる。
- `unresolved` はマスタに無かった語。検索には使われない。
- `degraded` は ③ をスキップしたことを表す。フロントが警告文を出し分ける。

エラー:

| ステータス | 条件 |
| --- | --- |
| 400 | `text` が空 / 200文字超 / 分割後20語超 |
| 429 | レート制限（既存機構に相乗り） |

**502 は返さない**（3.6）。

### 4.2 レイヤ構成

```
handler/ingredient_resolve.go        HTTP境界・text の長さ検証・エラー変換
        ↓
service/ingredient_resolve.go        IngredientResolveService（①②③と部分成功の組み立て）
        ↓
IngredientRepository（既存・無変更）  FindAll で166件を引き、正規化マップを組む
ResolutionRepository（新規）          解決キャッシュの読み書き
IngredientResolveGateway（新規）      LLM
```

依存の向きは `handler → service → repository`（`spec.md` 3.2）。インターフェースは service パッケージで定義する（依存関係逆転）。

```go
// IngredientResolveGateway は未解決語を食材名に対応づける外部サービス。
// RecipeSearchGateway（spec.md 3.3）と同じく、実装差し替えのみで
// プロバイダを切り替えられる状態にする。
type IngredientResolveGateway interface {
    Resolve(ctx context.Context, words []string, catalog []string) ([]GatewayResolution, error)
}

// GatewayResolution は1語ぶんの対応づけ。
type GatewayResolution struct {
    Word string // 問い合わせた語
    Name string // 対応づいた食材名。空文字は「該当なし」
}
```

`catalog` に渡すのは **`ingredients.name` の166件のみ**（`name_kana` は渡さない）。カナは①の完全一致で既に効いており、③に届く語は漢字・略語・カタカナ表記など**カナ一致で拾えなかったもの**に限られる。渡してもトークンが倍になるだけで的中率に寄与しない。

実装は `ClaudeResolver` / `DeepSeekResolver` / `StubResolver`（テスト）。構造化出力の指定方法はプロバイダごとに違うが、**このインターフェースの内側に閉じる**。

### 4.3 ③の失敗処理

| 事象 | 挙動 |
| --- | --- |
| タイムアウト（3秒） | リトライ1回 → 失敗なら `degraded: true` |
| 5xx / レート制限 | 同上 |
| 不正な JSON | パース失敗として `degraded: true`（リトライしない） |
| マスタに無い名前を返した | その語を `unresolved` に落とす。`degraded` は立てない |

最後の行が 3.5 の効果にあたる。ハルシネーションは障害ではなく「該当なし」として処理される。

## 5. データモデル

#### ingredient_resolutions

解決結果のキャッシュ。**free の利用者も未認証も共用する**（利用者に紐づかない）。

| カラム | 型 | 制約 |
| --- | --- | --- |
| input_word | text | PK（**正規化後**の語） |
| ingredient_id | uuid | NULL可、FK → ingredients(id) ON DELETE CASCADE |
| resolved_at | timestamptz | NOT NULL DEFAULT now() |

> **未解決（NULL）もキャッシュする。** 「マツタケ」はマスタに無いので `ingredient_id = NULL` で保存する。これをやらないと、マスタに無い語だけが毎回 LLM を通ることになり、**いちばん無駄な呼び出しが残り続ける**。

> **TTL を持たない。** `recipe_link_caches` は7日TTLだが、あちらはレシピ記事が変わるため。**食材の別名は変わらない**（「豚こま」が豚肉でなくなる日は来ない）。ただし食材マスタに新しい食材を足した場合、過去に `NULL` で保存した語が解決可能になるので、**マスタ更新時に `NULL` 行を消す運用コマンドを用意する**（9章）。

> **`ON DELETE CASCADE`。** `menu_ingredients` は `RESTRICT`（使用中の食材を消せなくする）だが、こちらはキャッシュなので、食材が消えたら解決も消えるのが自然。

> **PK は正規化後の語。** 3.4 の `NormalizeIngredientWord` を通した値を入れる。①の完全一致引きと**同じ関数**を通すことが前提。

## 6. フロントエンド

```
SearchByIngredientsPage
  ├─ IngredientTextInput   新規：textarea ＋「読み取る」
  ├─ ResolveResult          新規：未解決語・縮退の表示
  ├─ IngredientPicker       既存・変更なし
  └─ Matches                既存・変更なし
```

### 6.1 状態の流れ

```
[読み取る] → resolve mutation
              ↓ 成功
         setSelected(prev => prev ∪ resolved の ingredient.id)
              ↓
         IngredientPicker のチェックが更新される
         「N個を選択中」が role="status" で自動アナウンスされる（既存実装）
              ↓
         利用者が目で確認・修正
              ↓
         [この食材で探す] → 既存の searchByIngredients
```

**反映は「マージ」とする**（置き換えではない）。すでに手で入れたチェックを消さない。`Set` なので重複は吸収される。

### 6.2 未解決・縮退の表示

`IngredientPicker` は `max-h-[55vh]` のスクロール領域を持つため、**チェックが画面外に入って気づかれない**恐れがある。読み取り結果のパネルは**ピッカーの上**に置き、既存の「N個を選択中」（`role="status"`）と合わせて変化を伝える。

- 未解決あり: 「登録がありませんでした / マツタケ・パクチー（この2つは検索に使われません）」
- `degraded: true`: 「一部だけ読み取れました。残りは下から選んでください」

### 6.3 既存コメントの更新

`IngredientPicker.tsx` の先頭コメントは、現状この機能を否定している。

```ts
// 自由入力にしないのは、食材が自前マスタで表記揺れ（にんじん／人参）を
// こちらで吸収する必要が出るため。
```

**残すと嘘になる**ので、「解決は `/ingredients/resolve` が担い、このコンポーネントは確認・修正の UI に徹する」という趣旨に書き換える。`spec.md` 2.9 の同じ記述も、判断が覆った経緯を残す形で更新する（削除ではなく上書き）。

## 7. テスト戦略

**実 LLM を叩くテストは CI にゼロ。**

| 層 | 内容 |
| --- | --- |
| domain | `NormalizeIngredientWord` のテーブルテスト（全角/半角、カタカナ/ひらがな、空白、記号）。純関数なので最重要かつ最も安い |
| service | `StubResolver` を注入して下表を検証 |
| repository | `ingredient_resolutions` のスキーマと CRUD（既存 `*_schema_test.go` の流儀） |
| handler | 400（空 / 200文字超 / 20語超）、200 のレスポンス形 |
| frontend | `SearchByIngredientsPage.test.tsx` に追加。読み取り→チェック反映、未解決表示、縮退表示 |

service のテストが本体。特に以下は必ず書く。

| ケース | 期待 |
| --- | --- |
| 全語が①完全一致 | **Gateway が1回も呼ばれない** |
| ②キャッシュヒット | **Gateway が1回も呼ばれない** |
| ③で LLM が解決 | 結果が `ingredient_resolutions` に保存される |
| 同じ語を2回連続で解決 | 2回目は Gateway が呼ばれない |
| Gateway がエラー | `degraded: true`、①②の結果は返る |
| Gateway がマスタに無い名前を返す | その語は `unresolved`。`degraded` は立たない |

上2つが**コスト設計の核心**なので、「呼ばれないこと」をスタブの呼び出し回数で検証する。

### 7.1 eval ハーネス

`testdata/ingredient_resolution_cases.json` に正解データを置く。

```json
[
  { "input": "豚こま",   "expected": "豚肉" },
  { "input": "ブタこま", "expected": "豚肉" },
  { "input": "マツタケ", "expected": null },
  { "input": "ねぎ",     "expected": "長ねぎ" }
]
```

- 50〜100件を手で作る（表記揺れ・略語・マスタ外・曖昧語をバランスよく）。
- `go test -tags=eval ./...` でのみ実行。**CI では走らせない**（API キーと課金が絡むため）。
- 出力は「正解率・誤答一覧・トークン数・所要時間・概算コスト」。
- **同じデータで DeepSeek と Claude Haiku を回し、数字で本番のデフォルトを決める**（3.7）。

## 8. コストと濫用への手当て

未認証で公開するため、コストが利用者側に握られる。3層で受ける。

1. **既存のレート制限に相乗り**（本番は検索60req/分）。
2. **入力長の上限**（200文字 / 分割後20語）。超過は 400。
3. **`ingredient_resolutions` によるキャッシュ**。同じ語は世界で1回しか LLM を通らない。

3が効くため、**運用が続くほど LLM 呼び出しは逓減する**。日次のグローバル上限（キルスイッチ）は入れない。DAU が1人前後の現状では過剰であり、必要性は実測で判断する。

## 9. デプロイ・運用

新テーブルを1つ足すため、投入順序を守る（マイグレーションは自動デプロイに含まれない）。

```
1. ローカルから migrate up を本番 Neon に流す
2. main にマージ（自動デプロイ）
3. seed は不要（このテーブルは空で始まる）
```

`ingredient_resolutions` は新規テーブルで既存コードは参照しないため、**先に流しても現行の本番は無害**。逆順にすると、デプロイ後の一瞬だけテーブルが無く `/ingredients/resolve` が 500 を返す。

- LLM プロバイダの API キーを Cloud Run の環境変数に追加する。手順は `DEPLOY.md` に足す。
- **食材マスタを更新したら `ingredient_resolutions` の `NULL` 行を消す**（5章）。運用コマンドとして用意する。
- 誤った解決が保存された場合の訂正手段は、該当行の削除。
