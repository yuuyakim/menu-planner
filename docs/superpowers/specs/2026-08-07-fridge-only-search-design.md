# 冷蔵庫検索に「作れるものだけ」と「最大限使う」を足す（設計）

2026-08-07。フェーズ13（手持ちの食材から献立を探す）の拡張。

利用者から2つ挙がった。

> 「冷蔵庫にあるものを全部チェックしておいて、この中から作れるものだけを使う。
> この中以外で作れるものは出さないようにしたい。これは今の冷蔵庫から検索とは別口にしたい。
> 今の冷蔵庫から検索も取り持っておきたい」
>
> 「冷蔵庫のものを最大限使ってほしいという選択肢を出してもいいかも。
> なんか安く抑えたいという話もあるから」

## 1. 着手前に確かめたこと

フェーズ13 は「完全一致に絞ると候補がほぼ0件になる」ことを理由に、
**不足を許す形だけ**で作られている（spec.md 2.9）。今回はその逆を足すので、
まず「絞ると本当に0件なのか」を実データで測った。

`backend/db/seeds/menu_ingredients.sql` を集計した結果（献立380件・紐付け1646件、
1献立あたりの食材は3〜5種が中心で最大7種）:

| 手持ち食材の数 | 不足0で作れる献立 |
| --- | --- |
| 5 | 0件 |
| 10 | 11件 |
| 15 | 18件 |
| 20 | 33件 |
| 25 | 46件 |
| 30 | 58件 |
| 50 | 132件 |

（手持ちは出現頻度の上位から順に取った場合。上位は
玉ねぎ104 / ねぎ98 / 卵83 / 米73 / にんにく56 / 鶏もも肉55 / にんじん55 …）

**「0件になる」は食材を数個しか選ばない場合の話だった。** 13-C の記録にある
「玉ねぎ・じゃがいも・にんじんで不足0は1件も無かった」は食材3つでの実測で、
今回の「冷蔵庫にあるものを全部チェックする」という使い方（20件前後）では
30件強の候補が出る。**前提を足さずにそのまま成立する。**

調味料は `ingredients` に登録していない（spec.md 14.4）ため、
この「不足0」は最初から調味料抜きの意味になっている。追加の除外は要らない。

## 2. 決めたこと

| 論点 | 決定 | 理由 |
| --- | --- | --- |
| 画面の分け方 | **同じ画面に2つのつまみ** | 食材の選択を1つに保てる。別画面にすると同じ冷蔵庫の中身を2回チェックすることになる |
| 0件のとき | **0件と明言し、「あと1品」を別枠で出す** | 「この中以外は出さない」という約束を破らずに行き止まりを防ぐ |
| エンドポイント | **既存の1本にフィールドを足す** | 省略時の挙動が現行と同一になり、今の `/from-fridge` を壊さずに済む |

### 2.1 「探し方」と「並び順」は独立した2つのつまみ

```
探し方  (●) 足りないものがあってもよい     ← 現行
        ( ) この中だけで作れるもの         ← 追加

並び順  (●) 買い足しが少ない順             ← 現行
        ( ) 手持ちを多く使う順             ← 追加
```

「作れるものだけ」を選ぶと不足が全件0になるので、並び順のつまみは意味を失う。
**画面ではそのとき並び順のラジオを描画しない。**

ただし**サーバでは特別扱いしない**。`sort` の値は受け取ったまま使う。
サーバに「片方の値が意味を持たない状態」を作ると、その分岐に対応するテストと
将来の読み手への説明が要る。実際どちらの並び順でも結果が同じになるだけなので、
画面が隠すだけで足りる。

### 2.2 0件のときは「あと1品」を別枠で返す

食材を数個しか選ばなければ0件になる（1章の表）。何も出ないまま終わらせると、
利用者は次に何をすればよいか分からない。

一方で、勝手に「不足を許す」に戻すのは選んだ条件をシステムが外すことになり、
「この中以外で作れるものは出さないようにしたい」という要望に正面から反する。

**間を取る。** 「作れる献立はありませんでした」を先に明言した上で、
**見出しを分けて**「あと1品買えば作れます」を並べる。地続きに見せると
約束を破ったように見えるので、視覚的に切る。

## 3. API

`POST /menus/search-by-ingredients` に省略可能な2フィールドを足す。
**省略時の挙動は現行と完全に同一**（後方互換）。

```jsonc
// リクエスト
{
  "ingredientIds": ["...", "..."],
  "onlyMakeable": false,        // 省略可。既定 false（不足を許す＝現行）
  "sort": "missing_asc"         // 省略可。既定 missing_asc。他は matched_desc
}

// 200
{
  "matches":    [ /* MenuMatch */ ],
  "nearMisses": [ /* MenuMatch。missing がちょうど1件 */ ]
}
```

- `sort` は `missing_asc`（不足の少ない順 → 一致の多い順 → カナ順）と
  `matched_desc`（**一致の多い順** → 不足の少ない順 → カナ順）の2値。
  未知の値は400（既定に丸めない。利用者の指定を黙って読み替えない）
- `nearMisses` は **`onlyMakeable: true` かつ `matches` が0件のときだけ**埋める。
  それ以外は常に空配列。常に返すと無駄な計算とペイロードになり、
  画面側も「どちらを見ればよいか」が曖昧になる
- `nearMisses` も上位20件まで。並びは `matched_desc`（不足はどれも1件で並ばないため）
- `matches` / `nearMisses` はどちらも0件のとき `null` ではなく `[]`

## 4. サービス層

**SQL もリポジトリのインターフェースも変更しない。**

`FindMenuIDsByIngredientIDs` は「手持ちと1つでも重なる献立」を返す。
不足0の判定に必要な「候補献立の全食材」は `buildMatches` が既に引いているので、
絞り込みは Go 側の述語1つで足りる。

`IngredientService.SearchByIngredients` の処理順:

```
buildMatches                      … 現行のまま
  → onlyMakeable なら len(Missing)==0 で絞る
  → sort（つまみに応じて2種類）
  → 上位20件で打ち切り
  → matches が0件かつ onlyMakeable なら、
    絞る前の集合から len(Missing)==1 を拾い matched_desc で並べて20件
```

**切り詰めは必ず並べ替えの後。** 50食材を選ぶと不足0だけで132件出るため、
切ってから並べると上位を取りこぼす。

引数は増やさず、`SearchByIngredientsInput` を受ける形に変える
（`ids` に真偽値と列挙が続く並びは呼び出し側で読めない）。

## 5. 画面

`SearchByIngredientsPage` にラジオを2組足す。`IngredientPicker` は無変更。

- `onlyMakeable` が選ばれている間は並び順のラジオを出さない
- 0件のときは「この中だけで作れる献立はありませんでした。食材をもう少し選ぶと
  見つかりやすくなります」を出し、`nearMisses` があれば見出しを分けて並べる
- **つまみを変えたら前の結果を消す。** 13-E で食材を選び直したときに
  そうしたのと同じ理由。残したままだと、いまの条件の答えだと誤解させる
- 「不足0でも調味料は要る」の断り（14.4 / 13-E）は
  `onlyMakeable` の結果でも引き続き出す。**むしろこの経路でこそ要る**

ラジオの各組は `fieldset` / `legend` で囲む（8-D と同じ。囲まないと
支援技術もテストもどちらの組の選択肢か区別できない）。

## 6. テスト

既存19本に足す。境界に寄せる。

**サービス**

- 不足0だけが返る / 不足1件以上が混ざらない
- `onlyMakeable` 省略時に現行と同じ結果（後方互換の固定）
- `matched_desc` で一致の多い献立が先頭 / 同数なら不足の少ない方 / さらに同数ならカナ順
- 21件以上あるとき**並べてから切る**（切ってから並べる実装なら落ちる）
- 0件のとき `nearMisses` が埋まる / 0件でなければ空
- `nearMisses` は missing ちょうど1件だけ（2件は入らない）
- `onlyMakeable: false` のときは `nearMisses` が常に空

**ハンドラ**

- 未知の `sort` で400 / `onlyMakeable` が真偽値でなければ400
- 省略時に既定値が service に渡る
- 未認証でも200（現行の扱いを保つ）

**画面**

- つまみ切替で並びが変わる / `onlyMakeable` 中は並び順ラジオが出ない
- つまみを変えると前の結果が消える
- 0件のとき「ありませんでした」と「あと1品」が別の見出しで出る

**E2E** — 既存の `from-fridge.spec.ts` に「作れるものだけに切り替えると候補が減る」を1本。

## 7. 範囲外

- **マイグレーションなし。** 既存の `ingredients` / `menu_ingredients` だけで組める
- **履歴に記録しない。** 現行どおり（候補を並べただけでは献立が確定していない）
- **1週間分は出さない。** 冷蔵庫から週間献立を組むのは食材の重複配分の話になり、
  積み残しの「週間献立での共通食材の再利用」と同じ問題を解くことになる。別途
- **音声入力は含まない。** `INGREDIENT_RESOLVER_API_KEY` 待ちの自由記述読み取り
  （`670f68b` で画面から外してある）を戻すのが先

## 8. PR の分け方

**当初は3本に分ける想定だった**（API とサービス / 画面 / E2E と README）。
実際には `feature/fridge-only-search` の**1ブランチ・1PR**にまとめた。

理由は、分ける動機が「積んだブランチが行き止まりになるのを避ける」ことに
尽きていたため。13-C ではブランチを積んだ結果、先行PRがマージされた時点で
後続の行き先が行き止まりになり本流に届かなかった（PR #124 で回収）。
各PRのCIは緑のままなので検知できない。

**積まないなら、その事故は起きない。** 1本にまとめれば「先行のマージを
待って次を切る」手順そのものが要らなくなる。3本に割っても、API だけ
入って画面が無い状態・画面だけ入って E2E が無い状態が本流に一時的に
残るだけで、レビューの単位としても利点が無かった。

**13-C の教訓は残る。** 次に分ける必要が出たときも、
**積まずに1本ずつマージしてから次を切る**こと。分けないという選択は
その制約を回避する一手であって、制約が消えたわけではない。

コミットは工程ごとに分けてある（API → OpenAPI → 画面 → あと1品 → E2E）。
レビューはコミット単位で追える。
